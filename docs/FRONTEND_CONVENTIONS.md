# Uniconvert 프론트엔드 협업 규칙

## 확정된 화면 흐름

- `/`는 서비스 랜딩 페이지로 사용한다.
- 회원가입 후 온보딩은 `약관 동의 → 기본 통화 → 현지 통화 → 월 예산` 순서로 진행한다.
- 기본 통화는 하나만 선택하고, 현지 통화는 여러 개 선택할 수 있다.
- 시간대는 별도 입력 화면 없이 브라우저에서 자동 감지한다.
- 닉네임과 최초 지갑 잔액은 기획 확인 전까지 화면과 요청 값에 포함하지 않는다.
- OCR은 후순위로 두고 핵심 화면을 먼저 구현한다.

## 대시보드 범위

- 사이드바 순서는 `홈 → 지출내역 → 리포트 → 계산기 → 설정`으로 고정한다.
- 데스크톱에서는 사이드바를 항상 표시한다.
- 모바일 내비게이션은 디자인 확정 후 구현한다.
- 홈 화면에는 지출 입력, 지출 내역, Pots 화면으로 이동하는 진입 요소를 둔다.
- Pots는 핵심 화면 완료 후 UI를 구현하며 사이드바에는 추가하지 않는다.

## 컴포넌트와 스타일

- React 컴포넌트와 컴포넌트 파일은 PascalCase로 작성한다.
- 페이지와 컴포넌트 스타일은 CSS Module로 분리한다.
- 색상, 간격, 글꼴처럼 공통으로 사용하는 값은 `src/styles/tokens.css`에서 관리한다.
- 영어와 숫자는 Helvetica를 우선하고, 한글은 Pretendard로 표시한다.
- 전역 `index.ts` 배럴 파일은 만들지 않고 실제 파일을 직접 import한다.
- 다른 폴더의 모듈은 `@/` 경로 별칭을 사용하고, 같은 폴더의 CSS Module은 상대경로를 사용한다.

## 주석

- 코드를 읽으면 바로 알 수 있는 동작은 주석으로 반복하지 않는다.
- 기획 예외, 백엔드 협의 대기, 임시 처리처럼 코드만으로 알 수 없는 이유를 기록한다.
- 후속 작업은 `TODO`와 이유를 함께 작성한다.

```ts
// TODO: 소셜 로그인 API 확정 후 Google 로그인 요청을 연결한다.
```

## Git

- 기능 브랜치는 `feature/기능명`, 수정 브랜치는 `fix/수정명` 형식을 사용한다.
- 커밋 타입은 `feat`, `fix`, `style`, `refactor`, `docs`, `chore`, `test`를 사용한다.
- 커밋 하나에는 하나의 목적만 담는다.
- PR은 작은 스타일 수정 하나가 아니라 리뷰 가능한 기능 흐름 단위로 작성한다.

권장 PR 단위:

1. 공통 스타일과 공통 컴포넌트
2. 로그인과 회원가입
3. 온보딩 흐름
4. 대시보드 레이아웃과 홈
5. 지출 입력·목록·상세
6. 리포트와 계산기

## 백엔드·기획 확인 대기

- Google 소셜 로그인 지원 여부와 OAuth 연결 방식
- 일반 로그인 실패 응답 코드와 사용자 표시 메시지
- Access Token과 Refresh Token 전달·저장·재발급 방식
- 로그인 유지와 자동 로그인 정책
- 닉네임 입력 위치와 필수 여부
- 최초 지갑 잔액의 필수 여부와 입력 위치
- 월 예산과 최초 지갑 잔액을 같은 화면에서 받을지 여부
