# Uniconvert 보안 위협 모델

## 1. 목적과 범위

이 문서는 Uniconvert의 프론트엔드와 공개 API 사용 흐름을 공격자 관점에서 분석하고, 실제로 수행한 세 가지 보안 검증을 하나의 위협 모델로 연결한다.

- 서비스: 지출 관리 및 환율 변환 웹 애플리케이션
- 프론트엔드: React, TypeScript, Vite
- 배포: AWS EC2 기반 운영 환경
- 인증: Access Token과 Refresh Token을 `sessionStorage`에 저장
- 주요 기능: 지출, CSV 가져오기, 리포트, Pots, 메모, 카테고리, 예산
- 주요 API: `/auth`, `/users/me`, `/expenses`, `/reports`, `/exchange-rates`, `/pots`, `/memos`, `/currencies`, `/categories`, `/budgets`

검증은 소유한 테스트 계정과 허가된 서비스 범위에서 진행했다. 실제 토큰이나 개인정보를 외부로 전송하지 않았다.

## 2. 보호 자산

| 자산 | 보안 목표 | 침해 시 영향 |
|---|---|---|
| Access/Refresh Token | 기밀성, 무결성 | 계정 세션 탈취 및 API 오용 |
| 지출·예산·리포트 데이터 | 기밀성, 무결성 | 개인 금융정보 노출 또는 변조 |
| 사용자 프로필 | 기밀성, 무결성 | 개인정보 노출 및 계정 정보 변조 |
| CSV 원본 및 처리 정보 | 기밀성 | 거래내역·로컬 경로·내부 식별자 노출 |
| API 가용성 | 가용성 | 비정상 입력으로 인한 500 오류 및 서비스 불안정 |
| PWA Cache Storage | 기밀성 | 공유 기기나 오프라인 캐시에 민감 응답 잔존 |

## 3. 신뢰 경계와 공격 표면

```text
사용자 입력 / CSV
        │
        ▼
React UI ── sessionStorage(인증 토큰)
        │ HTTPS + Bearer Token
        ▼
api.uniconvert.dev ── 데이터베이스

브라우저
  └─ Service Worker Cache
       ├─ 정적 앱 셸: 캐시 허용
       └─ API·인증 응답: 캐시 금지
```

주요 공격 표면은 다음과 같다.

1. 브라우저에서 API 요청을 직접 변조하거나 인증 헤더를 제거하는 행위
2. 저장형 XSS를 통해 동일 출처 JavaScript 실행 권한을 얻는 행위
3. PWA 캐시에 인증 응답이나 개인 금융 데이터가 남는 행위

## 4. 위협 및 검증 매핑

| ID | 위협 | 공격 시나리오 | 대응 검증 | 결과 |
|---|---|---|---|---|
| T-01 | 인증 우회 | Bearer Token 없이 보호 API 호출 | Burp에서 `Authorization` 제거 | `401 Unauthorized`, PASS |
| T-02 | 요청값 변조 | UI 검증을 우회해 음수·0·잘못된 값 전송 | Burp Repeater 변조 | `400 Bad Request`, PASS |
| T-03 | 수치 범위 초과 | 초대형 금액으로 DB 숫자 범위 초과 유발 | 동일 요청 수정 전·후 재전송 | `500 → 400`, FIXED |
| T-04 | 사용자 간 데이터 노출 | 계정 A의 데이터를 계정 B로 조회 | 테스트 계정 분리 검증 | 노출 없음, PASS |
| T-05 | Stored XSS | 상호명·메모에 실행 가능한 HTML 저장 | UI와 Burp 우회 입력 후 재출력 | 문자열 출력, PASS |
| T-06 | XSS 발생 시 토큰 노출 | 동일 출처 스크립트가 `sessionStorage` 접근 | 저장 구조 및 JS 접근성 확인 | 잠재 영향 확인 |
| T-07 | 스크립트 주입 방어 부재 | 인라인·미허용 외부 스크립트 실행 | CSP 적용 전후 검증 | 차단 확인, RETEST PASS |
| T-08 | 민감 응답 캐시 잔존 | API·인증 응답이 Cache Storage에 저장 | 코드·Cache Storage·오프라인 검증 | 캐시 없음, PASS |

## 5. 우선순위 판단

| 우선순위 | 항목 | 판단 |
|---|---|---|
| 높음 | 초대형 금액 처리 | 실제 `500 Internal Server Error`가 재현되어 입력 검증을 보완하고 재검증함 |
| 중간 | CSP 부재 | 직접적인 XSS는 없었지만 향후 결함의 실행 가능성을 낮추는 추가 방어선이 필요함 |
| 중간·장기 | `sessionStorage` 토큰 | 현재 XSS는 재현되지 않았으나 XSS 발생 시 토큰 접근 가능. 백엔드 계약과 CSRF 설계를 포함해 개선해야 함 |
| 유지·회귀검증 | PWA 캐시 범위 | 현재 설계가 안전하므로 서비스워커 변경 시 API 제외 정책을 회귀검증해야 함 |

## 6. 결론

즉시 악용 가능한 Stored XSS나 인증 우회는 확인되지 않았다. 실제로 발견한 문제는 초대형 금액 입력이 서버 내부 오류로 이어지는 수치 범위 검증 누락이었고, 범위 검증을 추가한 뒤 같은 요청이 400으로 차단되는 것을 확인했다. CSP는 방어 심층화를 위해 적용했으며, PWA는 정적 자산만 저장하고 개인 API 응답을 캐시하지 않는 구조임을 확인했다.
